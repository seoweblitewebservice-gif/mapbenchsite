# Tool page patterns: representative audit

Reviewed publicly accessible competitor pages for county lookup, coordinate finder, KML viewer and drive-time map on 2026-10-28, alongside the previously documented midpoint and radius examples. These are samples, not an audit of every competitor tool or a test of the competitor's interactive implementation.

## Observed patterns
- The interactive interface appears before the detailed explanatory sections; instructions follow and describe the actual task. Long explanations use headings, examples, methodology, limitations, related links and FAQs where applicable. The coordinate page includes a table of contents; the file viewer identifies supported and unsupported formats. County and routing pages distinguish coverage and model assumptions.
- Competitor claims and examples are not independent verification of MapBench's features, coverage or results. For example, coordinate precision is not itself measurement accuracy, and a travel-time polygon is not a live-traffic guarantee. Do not reuse competitor text, calculations or data.

## MapBench review and implementation
- `ToolClient.tsx` already implements a registry-backed page shell with one H1, workspace, instructions, optional authored content, method notes, FAQs and contextual links. `distance-matrix-calculator` uses a separate route and was handled separately. Existing `content/*.json`, registry data, methods, links, page metadata and tool implementations are retained.
- Added direct links to the workspace and usage instructions; improved contents navigation and typography; removed a misleading static “Ready” indicator and wording that assumed every tool has a map. Related descriptions no longer visually truncate. These changes are original and shared across the regular tool template and the dedicated matrix route.
- The competitor analysis informed the hierarchy, not the page copy or data. No claim is made that 496 individual tools, their output, examples, data sources, or all existing authored content have been independently validated.

## Remaining priorities
1. Review each tool's authored instructions, examples, coverage, source claims and current behavior against its implementation; prioritize popular and external-service-dependent tools. Where evidence is missing, correct or qualify the copy individually rather than adding generic text.
2. Test browser behavior at mobile and desktop widths, keyboard interaction, map rendering, downloads and routing/geocoding service failure modes. Check actual deployment origin and consent settings.
3. Review duplicate/boilerplate content, metadata and structured data with a rendered-page crawler and current search-engine guidance. Do not add schema solely for a rich result or assert guaranteed rankings/approval.

## Follow-up: all-tool inventory and trust corrections

The registry audit checked all 496 canonical slugs, matching content files, registered component keys and internal tool links. It identified 159 tools without a registry-level implementation-specific method; a category-level caution is not a substitute. Content-depth counts are an inventory only, not a factual review or quality target.

Review of the location and IP components found that some location controls use ipwho.is, with ipapi.co fallback, without browser GPS permission. The privacy page previously described all location controls as browser GPS only and did not name those providers. The privacy and data-sources pages now describe those requests and their approximate nature. Provider terms and any legal or consent implications still require owner review.

Removed three broadly applied but irrelevant category-to-guide links: network/IP tools to geographic routing, geographic reference lines to land-area measurement, and all location tools to meeting-point selection. Specific tool overrides still provide the meeting-point guide where relevant. No routes or tool behavior changed.

The category template claimed that every page has its own documented method. Since the all-tool audit found 159 registry entries without implementation-specific method text, category descriptions now say that detail varies instead of making a universal claim. Individual tool metadata and canonical URLs are unchanged. Exact duplicate checks across all content JSON records found no identical non-empty titles, descriptions, quick answers, summaries or step introductions; this is not a semantic-duplication or factual-accuracy audit.

A source-level review of the two network tools found that public-IP detection requires a button press and contacts ipwho.is; it does not automatically run on opening the page. Added implementation-specific method notes for both network tools, corrected the public-IP instructions, and qualified assertions that a single IP comparison proves a VPN leak. The remaining count without registry-level method text is 157. A lookup by itself cannot establish full VPN or DNS protection.

## Subsequent code-level findings

- The `multi-radius-map` and `service-coverage-gap` registry entries did not enable their radius component's multiple-circle mode. Enabled the existing mode; it does not calculate an optimal site or guarantee road access.
- The geohash page promised decoding, but its converter only encoded. Added decoding to the cell centre and regression checks; this is not the exact original point. The converter's supported-input description now mentions the distinction.
- The radius FAQ called its calculation a WGS84 geodesic although the implementation uses spherical destination formulas. Corrected that claim and added method notes for radius, multiple-radius, distance and geohash tools.
- The shared converter does not implement GARS, British National Grid, Irish Grid, State Plane, H3 or quadkey transformations; the trail estimator's distance workspace measures two endpoints, not a drawn path. Added conspicuous limitations on those seven pages instead of presenting those features as available. Existing longer copy on these pages still needs a line-by-line accuracy review and may contain conflicting claims; the warning is not a substitute for implementing the missing features or revising their content.
- This review is incomplete. In particular, the registry audit identifies 152 tools without implementation-specific method text, and no browser-based verification of every calculator, download, map, external service, or mobile layout has been performed.

### Further route-family review

The equidistance page previously used the initial bearing at A to draw a two-point straight segment, which is not generally the spherical perpendicular bisector at the midpoint. It now samples a bounded spherical arc using the midpoint bearing, rejects degenerate pairs, and describes map interpolation and road-time limitations. Regression tests compare spherical distances at every sample, including an antimeridian case. The two postal-centroid pages used a vector mean but claimed it minimised mean distance; corrected that claim, disclosed external lookups, exposed the 25-code cap instead of silently truncating, and reject a non-unique vector mean. Canada is appended to the Photon query rather than enforced as a country filter; this limitation is now documented. Stage-day inputs are clamped and excessive stage requests rejected. External-provider and browser interaction behaviour still needs live verification.

### Nearby finder review

Reviewed the ten `list-nearby` page workspaces and their prominent copy, output tables and relevant FAQs against their actual OSM queries. Corrected unsupported hours, accessibility, connector, trail-length and emergency-service claims; explained the narrower station query and added emergency warnings for hospital modes. Searches now clear stale results and ignore an obsolete Overpass response after changing the centre or radius. ### British grid / postcode family

Service availability and browser behavior have not been tested live; remaining educational and historical assertions still require verification.

### Earth, weather and astronomy family

### File-viewer family pass

Inspected eight shared file-viewer registrations plus the two focused file tools. KML/KMZ claims now match the uncompressed KML parser; added actual LineString length calculation with separate-segment regression coverage and strict KML coordinate validation. Three aliases still lack WKT conversion, GeoJSON simplification, or GPX speed/pace calculations; prominent limitations and revised copy state this rather than promising them. GPX heart-rate bands are fixed BPM sample shares, not time-weighted or personalised; corrected the workspace, metadata, table and safety wording, and stopped summing distances across distinct GPX segments. Photo routes are straight-line joins, EXIF time is interpreted in browser local time with file modification fallback, and map tile requests may reveal the viewed area. GPX export now preserves point feature names and valid timestamps, with regression coverage; other metadata/geometry can still be lost and the UI says so. Browser-based file upload, external tiles, the full XML/EXIF format range and every remaining long-form factual claim have not been individually verified.

Follow-up: corrected the KML path-length table and FAQ (polygon boundaries are not measured), removed an unverifiable numeric example, and described one-file-at-a-time comparison. GPX profile now plots cumulative within-segment distance rather than point index and breaks strokes at segment/elevation gaps. Invalid GPX coordinates also split map lines, and timestamp extrema no longer use spread arguments that can overflow on large tracks. Added profile regression coverage; XML parsing and browser rendering still need direct tests.

### Map-data family follow-up

Country selection has 24 options and Nominatim's first polygon match is not verified as a complete country; its preview fits only the first outer ring. No live Overpass, Nominatim, OpenFlights, embed, export or browser interaction tests have been conducted; not every long-form statement in these six pages was verified.

### Spatial-analysis family follow-up

Inspected six `list-spatial` workspaces and corrected prominent copy. Voronoi cells use planar longitude/latitude degrees within an automatically padded rectangle, not reliable geodesic or road catchments. Buffer and dashboard counts are capped node-only Overpass responses; ways, relations and unmapped objects are omitted, and displayed circle areas use planar πr². Some controls can change during pending requests and should be reviewed for stale results in a future pass.

Spatial request follow-up: changing centre, radius, weights, candidate names or endpoint now invalidates the current result and prevents older replies from replacing it. In-flight provider requests are not aborted, although the suitability loop stops after its current request completes. Browser interaction tests remain outstanding.
